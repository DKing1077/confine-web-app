# Docker + Web App (Flask) — Complete Concise Notes

---

# 1. What Docker is
Docker runs applications inside isolated environments called containers.

A container bundles:
- Application code
- Dependencies (Python, system libs)
- Runtime (Python version, OS libraries)

Result:
- Same behavior on every machine
- No “works on my machine” issues

---

# 2. What a container is
A container is:
- A lightweight isolated process
- Built from an image
- Shares host OS kernel (not a full VM)

Key properties:
- Fast startup
- Reproducible environments
- Isolated networking + filesystem

---

# 3. Docker Compose (your setup)

docker-compose runs multiple services together:

### Your stack:
- web → Flask API
- postgres → database
- redis → cache / broker
- celery → background worker

It handles:
- service networking
- environment variables
- startup orchestration

# 5. docker-compose.yml (your config explained)

services:
  web:
    build: .
    command: python run.py
    ports:
      - "5001:5000"
    environment:
      - DB_HOST=postgres
      - DB_PORT=5432
      - REDIS_URL=redis://redis:6379/0

---

## Why environment variables are REQUIRED

### 1. Config is environment-specific
Inside Docker:
- DB is NOT localhost
- Redis is NOT localhost

Instead:
- postgres → database container
- redis → redis container

So this must exist:
DB_HOST=postgres
REDIS_URL=redis://redis:6379/0

If you used:
localhost
it would break (points to container itself).

---

## 2. Why services use names instead of IPs
Docker provides internal DNS:

- postgres → resolves automatically
- redis → resolves automatically

No hardcoded IPs needed.

---

## 3. Port mapping explanation

"5001:5000"

Means:
- 5000 = inside container (Flask)
- 5001 = your machine (browser)

So access is:
http://localhost:5001

---

# 6. Flask startup (IMPORTANT)

app.run(host="0.0.0.0", port=5000, debug=True)

## Why 0.0.0.0 is required
- 127.0.0.1 = only inside container
- 0.0.0.0 = exposed to Docker + host mapping

Without it:
- app runs but is unreachable externally

---

# 7. Dockerfile (typical for your app)

FROM python:3.11-slim

WORKDIR /app

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 5000

CMD ["python", "run.py"]

---

## Why each line matters

FROM python:3.11-slim
- Base Python environment

WORKDIR /app
- Sets working directory

COPY requirements.txt
- Enables dependency caching

RUN pip install
- Installs dependencies inside container

COPY . .
- Copies application code

EXPOSE 5000
- Declares internal port

CMD python run.py
- Starts the application

---

# 8. Why copying config matters (critical concept)

Your app depends on:

- DB_HOST
- DB_USER
- DB_PASS
- REDIS_URL

Without them:
- app cannot connect to services
- defaults to localhost → breaks in Docker

---

## Why env vars instead of hardcoding

Hardcoding:
localhost, passwords, URLs

Problems:
- breaks in Docker
- not portable
- insecure
- impossible to deploy cleanly

Env vars:
- flexible
- secure
- environment-specific
- production standard

---

# 9. Key Docker Compose commands

Build and run:
docker-compose up --build

Stop:
docker-compose down

Logs:
docker-compose logs web

Live logs:
docker-compose logs -f

Reset everything:
docker-compose down -v
docker-compose up --build

---

# 10. Flask debug mode (important in Docker)

debug=True enables:
- auto reload
- debugger
- restart on file changes

Problem in Docker:
- restarts break DB connections
- causes instability

Optional fix:
use_reloader=False

---

# 11. Celery role

Celery runs background tasks:

Examples:
- heavy computations
- async processing
- API jobs

Flow:
Flask → Redis → Celery → Postgres / APIs

# 12. Common issues in your setup

1. App not accessible
- missing 0.0.0.0
- missing port mapping

2. DB connection errors
- Flask reloader restarting app
- stale connection pool

3. Celery warnings
- running as root
